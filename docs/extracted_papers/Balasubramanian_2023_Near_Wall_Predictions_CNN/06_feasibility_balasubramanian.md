# Feasibility Analysis & Data Pipeline Audit
### Target: Balasubramanian et al. (2023) — CNN Wall Predictions

## 1. Data Pipeline Audit (Primary Bottleneck)

### Origin & Access — ⚠️ REQUEST-ONLY, NOT a public download
The data is **not** on Zenodo/Figshare/public mirror. Lineage:
- This paper reuses the dataset from **Guastoni et al. (2021)**, generated by the **SIMSON** pseudo-spectral solver (Chevalier et al., 2007) — a DNS of turbulent open-channel flow.
- The companion code is [`KTH-FlowAI/FCN-turbulence-predictions-from-wall-quantities`](https://github.com/KTH-FlowAI/FCN-turbulence-predictions-from-wall-quantities). Its **Data** section states verbatim: *"the dataset… are available… Please, get in touch using the email address for correspondence in the paper to arrange the transfer."*

**Implication:** acquisition requires an **email handshake with KTH** (manual, latency of days–weeks) or **regenerating the DNS yourself in SIMSON** (Fortran, HPC-class, non-trivial). Neither fits a "clone-and-run" autonomous batch pipeline. This is the hard gate.

### Storage & Memory Footprint — MODERATE (disk-bound, not VRAM-bound)
Single-precision (`float32`) raw field estimates:

| Config | Field | Per-field | ×3 comp (u,v,w) | Total (3-comp) |
|---|---|---|---|---|
| $Re_\tau=180$ | $192^2$ × 50,400 | 0.14 MB | 0.42 MB | **≈ 21 GB** |
| $Re_\tau=550$ | $512^2$ × 19,920 | 1.0 MB | 3.0 MB | **≈ 58 GB** |

- These are **per wall-normal plane**. With 5 sampled planes ($y^+=15,30,50,100,150$) plus 3 wall quantities retained for the wall-prediction task, the full corpus balloons to **~100–150 GB**. Feasible on a local SSD, awkward to move over email/transfer.
- **MPS/compute memory is a non-issue:** model = 2.9M params (~11 MB); a batch of 8×3×$192^2$ float32 ≈ 3.4 MB. Training fits comfortably on an M-series MPS. **The constraint is dataset storage + I/O throughput, not GPU RAM.**

### Preprocessing Risk — LOW (but not `torchvision.transforms`)
- **Periodic padding (32/side):** trivially reproducible with `torch.nn.functional.pad(x, (32,32,32,32), mode='circular')` inside a custom `Dataset`/model — **not** `torchvision.transforms` (those target RGB images and don't do physically-correct circular padding on multi-channel fields). Then center-crop the output back to DNS size. Low risk.
- **RMS normalization (Eqs. 2–3):** straightforward per-component scaling in a custom `Dataset`, **but** requires the precomputed RMS constants from the training split — and the modified-ReLU thresholds ($-1$, $-25$) are only valid if the normalization exactly matches the paper's. Low risk, one dependency.

## 2. Architecture Implementation Complexity — ⚠️ MEDIUM (exact topology gap)
- **Crop-on-concat itself is easy:** center-crop the upstream feature map to the downstream spatial size, then `torch.cat([down, cropped_up], dim=1)`. No up-sampling needed. ~Medium-low effort.
- **The real gap:** the **exact per-layer kernel counts** for the 31-layer FCN/R-Net are shown **only in Figure 1** (an image, `_page_7_Figure_0.jpeg`) — they are **not in the extracted text**. The markdown gives layer count (31), kernel size ($3\times3$), param totals (2,902,791 / 2,568,681) and skip topology ($i \leftrightarrow N-i-1$), but **not the channel width of each layer**. You must either (a) read the figure by eye, (b) back-solve widths to hit the exact param counts, or (c) email the authors.
- **No PyTorch reference exists:** the public repo is **TensorFlow, FCN-only**. FCN-POD and **R-Net are not released** ("only the FCN implementation is provided"). Everything is a from-scratch PyTorch port.

## 3. Physics Validation Gate Feasibility — ⚠️ BLOCKED on data
- **Gate 3 ($R \ge 0.8$)** and **Gate 4 (2D pre-multiplied PSD contours)** both require the **raw DNS reference fields** to compute ground-truth correlations and spectra. There are **no shipped benchmark tables** of these spectra in the paper or repo.
- Since the DNS data is request-only (§1), **you cannot validate Gate 3/4 until the KTH transfer completes.** The only self-contained artifacts are the paper's summary error tables (Tables 1–4), which can serve as *sanity targets* but not as pixel-level spectral references.

## 4. Final Verdict

### 🟡 FEASIBLE WITH ADAPTATION

The pipeline (architecture, preprocessing, gates) is technically reproducible on local M-series hardware — compute and memory are not limiters. The blockers are **data provenance and specification completeness**, not modeling.

**Immediate missing links (in priority order):**
1. **🔴 Dataset access** — no public download; must email KTH to arrange transfer (or regenerate via SIMSON). *Blocks Gates 3 & 4 and all training.* This breaks the "autonomous batch" premise for this paper.
2. **🟠 Exact R-Net topology** — per-layer kernel widths live in Figure 1 (image only). Back-solve to the 2,568,681 param target or contact authors.
3. **🟠 No PyTorch/R-Net reference** — public code is TF + FCN-only; port R-Net + crop-on-concat from scratch.
4. **🟡 RMS normalization constants** — must be derived from the (still-unobtained) training split to keep the $-1$/$-25$ output thresholds valid.

**Recommended next action:** treat this paper as a **spec-only tracer bullet** — build and unit-test the PyTorch R-Net skeleton against *synthetic* $192^2$ tensors now (validates crop-on-concat, padding, param count), and fire off the KTH data request in parallel so acquisition latency overlaps development.
